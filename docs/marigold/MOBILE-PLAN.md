# The phone wallet: a step-by-step plan (iOS and Android)

Decided 2026-10-12 (DECISIONS "The phone wallet: one Rust core, a React Native screen"). This is the executable plan: steps `PH-M0`–`PH-M12`, each with what to do, how it is verified, and when it is done, written so that one agent can take them one at a time in order. Steps are named `PH-M0` to `PH-M12` (PH for the phone), and a commit or branch for a step starts with that name, so that `PH-M8:` is never taken for the mining pool plan's `M8` (REPOS.md). Tick a step only when its verify line passes. Keep the basic look for now; the screens are tweaked later, the structure is not.

## Rules that hold for every step

- **One wallet implementation.** Every wallet operation on the phone goes through the Rust service (`WalletService`, today in `cli/src/serve.rs`, moved to its own crate in PH-M1). No JavaScript, Swift or Kotlin ever signs, derives a key, builds a transaction, reads a note file or parses a payment code; the phone side only calls the service and shows what it answers. Where the service lacks an operation the phone needs, the operation is added to the service, tested there, and then called.
- **Test against the public testnet.** The phone talks to `wss://rpc1.marigold.cash` (testnet-10) exactly as the terminal's `connect public` does; faucet notes come from the faucet. Nothing is mocked that can be real.
- **Every step leaves the desktop and the Telegram bot working.** They use the same service; after each step `scripts/build-gui.sh` builds and the terminal drivers pass.
- **Words a grandmother understands** on every screen and in every message (DECISIONS "Grandma safe"); technical detail only behind a settings switch.
- **No secret in the repository.** Signing keys, store credentials and the updater key live in the organisation's accounts and the workflow secrets; the plan names where, never what.
- **Builds:** Rust for the phone targets builds on the macOS runner the desktop already uses (`gui-binaries.yaml`) and on Ubuntu for Android; pve3 is not involved. Local iOS work needs a Mac.

## How an agent works a step

Read [REPOS.md](REPOS.md) first: it says which repository a piece of work belongs in and how a session behaves in a checkout. One step, or one lettered sub-step, is one branch `mobile/PH-M3a` and so on, in your own worktree (`git worktree add ../mobile-M3a -b mobile/PH-M3a origin/main`), pushed; it reaches `main` by fast-forward when its box is ticked, in the same session. Read the step, the rules above, and the files it names before touching anything. Do only what the step says, and before every commit read `git show --stat HEAD` and every hunk: another session's edit that is lying in a shared tree is how a foreign change gets into a commit, and it happened on PH-M1a; something missing from the plan that the step needs is added to the plan in the same pull request, as a new lettered sub-step, not done silently. Run the verify line and paste its output into the pull request; CI must be green. Tick the box in this file in that pull request. If the verify line cannot pass, say so in the pull request with the reason and stop; do not loosen the verify line. A `--locked` build proves the lock file only if no plain build touched it first: `scripts/remote-build.sh` runs a plain `cargo check` after the sync, which rewrites the lock on the build host, so after it compare `md5sum Cargo.lock` on the build host with the committed file and require them equal (`PH-M1a`'s own `--locked` run missed that, and main's lock had been stale since bd20b942; `PH-M1b1` fixed the lock). Build in a directory of your own on the build host, `MARIGOLD_BUILD_DIR=/opt/marigold-build/remote-build-<step> scripts/remote-build.sh ...` (and the same variable for `scripts/build-gui.sh`): the default directory on pve3 is shared, two syncs from two trees interleave, and a build then fails on code that is not yours. Versions of Expo, UniFFI and the phone toolchains are the current stable ones at the time of the first mobile commit, pinned in `mobile/package.json` and `wallet/service/Cargo.toml`, and bumped only in a commit of their own.

## Architecture in one paragraph

The Rust wallet core (`wallet/core`, with the light wallet in `light.rs`, and the service in `wallet/service`) is built in this repository and compiled natively for `aarch64-apple-ios`, the iOS simulator and `aarch64-linux-android` (plus `x86_64-linux-android` for the emulator), wrapped by UniFFI, which generates the Swift and Kotlin bindings, and exposed to React Native through one Expo native module, `@marigold/core`, which lives with the app in `marigoldcash/expo-mobile` and takes the compiled core from the release as a download. The app is TypeScript under Expo, with a development client (not Expo Go, which cannot load native modules). The service runs inside the app process; the light copy of the pool lives in the app's own storage; keys stay in the app's sandbox with the password in the platform keystore behind biometrics. The node is a public computer by default and configurable.

### [x] PH-M2 — The core builds for the phones

Do: add the four phone targets to `rust-toolchain.toml` and to a new workflow `mobile-core.yaml` (macOS runner for the Apple targets, Ubuntu with `cargo-ndk` for Android). Build `kaspa-wallet-service` as a static library (`crate-type = ["staticlib", "cdylib", "rlib"]`) for each target. Fix what does not compile: expect `getrandom` features, `mio`/`tokio` features, and C dependencies (`secp256k1`, `rocksdb` must not be pulled: confirm with `cargo tree`). Produce an XCFramework for Apple and a `jniLibs` tree for Android as workflow artifacts.

Verify: the workflow is green on all four targets and uploads the two artifacts; `nm` on the iOS library shows the symbols. Done when: a tag's workflow run produces downloadable libraries. Done 2026-10-13: `.github/workflows/mobile-core.yaml` (by hand and on every push to a `mobile/` branch) runs `scripts/mobile-core.sh`, which builds the phone and emulator `.so` files for Android (API 24, 16 KB page alignment, which Google Play wants) and an XCFramework with an iPhone slice and a simulator slice (iOS 15.1), each checked for the symbol `marigold_core_version`, and uploads `marigold-core-android` and `marigold-core-ios`. What it found: `reqwest` with `ring`, `secp256k1-sys` and `blake3` all build for the phones with the stock NDK and Xcode, and `rocksdb` is not in the tree (`secp256k1` is, and is a C library; the plan's expectation that it would not be was wrong, and it costs nothing). The one change to existing code is that `kaspa-hashes`' build script had no case for Android on x86_64, and now uses the ELF assembly it already ships for Linux. Two choices differ from the text above: the library kinds are asked for on the command line (`cargo rustc --crate-type cdylib` or `staticlib`) rather than set in the crate's manifest, so every other build of the crate stays an ordinary library, and the Android libraries are built by the script with the NDK's own clang rather than `cargo-ndk`, so the release job has one fewer tool to install. The `ffi` feature holds one C function for now (`marigold_core_version`); PH-M3a replaces it with the UniFFI interface. The Apple half cannot be run on pve3, so it was proved on the macOS runner; the Android half was also run on pve3 against an NDK kept in `/opt/marigold-build/ndk`, used only for checks.
